# Height in Art — Design Document

## Application Flow

### 0. Calibration (operator, one-time before public use)
Calibration happens on a dedicated `/calibration` page. A person of known height (the calibrator) is used — not an object.

**Calibration page layout**: live webcam feed alongside step-by-step instructions:
1. Mark a spot on the floor where users will stand.
2. Have the calibrator stand on that mark so their entire body is visible in the webcam.
3. The calibrator performs the trigger gesture (see §1 below) while facing forward.
4. The system analyses the calibrator's relative pixel height.
5. The calibrator enters their actual height (UI accepts cm or ft/in with a unit toggle).
6. The system stores the pixel-to-cm ratio; the calibrator is prompted to return to the home page.

- Calibration stores the ratio in `localStorage` so it survives page refreshes and browser restarts.
- If no calibration exists when a user arrives, the home page shows a **prominent banner** linking to `/calibration`.

### 1. User height measurement
The user stands in front of the webcam. ml5.js `bodyPose` (MoveNet) detects keypoints continuously. When the user makes the **trigger gesture**, the app:
- Measures the pixel-distance between the nose/top-of-head keypoint and the ankle keypoints.
- Multiplies by the calibration ratio to get height in cm.
- Handles partial occlusion: falls back to estimating height from visible keypoints using body proportion ratios; shows a mild persistent warning that full-body visibility gives best results.

**Trigger gesture** (same for calibration and regular users): standing facing forward with hands at sides, sweep one hand in a full circle — across the body, above the head, and back to the side — while continuing to face forward.

Implementation: track the wrist keypoint trajectory over a rolling ~1–2 second window and confirm the phase sequence (hip → cross body → above head → hip) in order. Chosen because it is large enough for reliable detection and unlikely to be made unintentionally.

### 2. Object matching
The app loads `data/height_index.json` (2.1MB) at startup — an array of `[object_id, height_cm]` pairs sorted by height. When a user height is measured, the app selects a **random combination** of objects whose heights sum to approximately the user's height (within a tolerance — TBD).

**Tolerance**: sum of object heights must be within ±5% of the user's height. No target number of objects — keep selecting until the sum is within tolerance.

**Object constraints**:
- No more than 3 objects shorter than 2cm in any matched set.
- No more than 1 object taller than 100cm in any matched set.

Matching strategy: greedy random — pick a random eligible object (respecting constraints), subtract from remaining height, repeat. Objects taller than the remaining sum are excluded each step. If no valid combination is found within ±5%, retry silently up to 100 attempts; if all fail, progressively relax the tolerance until a match is found.

Objects with missing images are excluded from the eligible pool at startup (pre-filtered via a list generated by the Python pre-processing step).

If multiple people are in frame, the person who performs the trigger gesture is measured.

### 3. Display
Left panel: captured still frame of the user at the moment objects are revealed; after 0.5 seconds switches back to live webcam feed so the next user can get into position.

Right panel: stacked column of matched object images. Each image maintains its own aspect ratio. Objects animate dropping one on top of the other from above — successive objects begin their drop without waiting for the prior object to land. No labels are shown on the stacked images.

If `object_metadata.json` is still loading when a match is made, a loading indicator is shown where the QR code will appear until the file is ready.

A small "recalibrate" link is always visible in a corner of the home page.

### 4. QR code
After a match is made, a QR code appears to the **right** of the canvas (in `#qr-sidebar`, a sibling flex item — not overlaid on the canvas). The sidebar is bottom-aligned with the canvas so the QR code and caption sit at the canvas's bottom edge.

The QR code links to `info.html` with object data base64-encoded in the URL. `buildQRCode()` tries four progressively smaller payloads until one fits within QR code capacity (~2953 bytes):
1. Full metadata (title, artist, date, medium, department, culture, link, height_cm)
2. Slim (id, title, artist, link, height_cm)
3. Terse (id, truncated title ≤40 chars, link, height_cm)
4. Minimal (id, height_cm only) — always fits

The info page shows a vertical scrolling list of cards — one per object — each with title, artist, date, medium, and a link to the Met website. When the payload is minimal (level 4), the info page fetches full metadata from the Met Museum API on arrival.

## Data Architecture

### height_index.json (2.1MB — loaded by main app)
```json
[[34, 61.9], [41, 15.9], [42, 78.4], ...]
```
Sorted ascending by height. Used exclusively for matching. Small enough to load at startup with no noticeable delay.

### object_metadata.json (51.8MB — NOT loaded by main app)
```json
{
  "34": { "title": "Acorn Clock", "artist": "...", "date": "...", ... },
  ...
}
```
Full display metadata for all 154,001 objects, keyed by object_id string. Too large to load in the browser at runtime.

## Info Page Data Strategy

The info page is opened by scanning a QR code on a phone — it **cannot** share sessionStorage with the main app. Passing object IDs in the URL is trivially small. The question is purely **how the info page retrieves metadata for those IDs**.

### Why not follow pose_match exactly?
pose_match passes a single `?id=` and the info page loads a small local `input_image_metadata.json` to look it up. That works because pose_match's reference set is curated and fixed — the file only covers the specific images used by the app. height_in_art draws from 154,001 possible objects, so no equivalent small file can be prepared in advance. Our full metadata file is 51.8MB.

### Chosen approach: embed metadata in the QR URL, with Met API fallback

The main app base64-encodes a compact JSON snippet of the matched objects' metadata into the URL:
```
info.html?data=<base64 of [{id, title, artist, date, height_cm, ...}, ...]>
```

**Four-level payload fallback**: QR codes have a hard capacity limit (~2953 bytes at medium error correction). `buildQRCode()` tries payloads in decreasing size until one fits:
1. Full metadata
2. Slim (id, title, artist, link, height_cm)
3. Terse (id, title truncated to 40 chars, link, height_cm)
4. Minimal (id, height_cm only) — always fits

**Info page behavior**:
- If the payload contains `title` fields (levels 1–3), the info page renders immediately — no network calls, works offline.
- If the payload is minimal (level 4, only id + height_cm), the info page fetches full metadata from the Met Museum API (`https://collectionapi.metmuseum.org/public/collection/v1/objects/{id}`) for each object in parallel, shows "Loading artwork details…" while waiting, then renders the enriched cards. QR scanning implies the user has a phone with internet, so this is acceptable.

**Important**: what is encoded is metadata **for just the matched objects**, not just their IDs. The base64 encoding carries structured data safely in a URL rather than obfuscating IDs.

**Why not load object_metadata.json on the info page**: `object_metadata.json` is 51.8MB — loading it on arrival would produce a noticeable delay at exactly the wrong moment. Instead, the 51.8MB file loads in the background on the index page while the user is occupied with calibration and height measurement. By the time the user scans the QR, metadata has already been extracted and the URL built. When the full payload fits (most cases), the info page opens instantly.

**Implementation note**: `object_metadata.json` begins loading in the background immediately after `height_index.json` finishes. The QR code is not displayed until both are available and a match has been made.

## File Structure

```
height_in_art/
├── index.html              # Main app — pose detection, object matching, drop animation, QR
├── sketch.js               # p5.js / ml5.js logic
├── calibration.html        # Operator calibration page
├── info.html               # Multi-object info page (opened via QR on visitor's phone)
├── about.html              # About page (content TBD)
├── gesture-animation.js    # Animated stick figure (plain canvas, no p5 dependency)
├── ml5.min.js              # Local ml5 build (CDN version lacked detectStart; pose_match/.gitignore excluded it from that path)
├── branding.js             # CSS custom properties
├── analytics.js            # Analytics stub
├── branding/               # Fonts, logo, favicon
├── pose_match/             # Sibling reference project (visual design reference)
├── data/
│   ├── height_index.json       # 2.1MB — loaded at startup
│   ├── object_metadata.json    # 51.8MB — loaded lazily in background
│   └── small_images/           # ~154k JPGs, named {object_id}.jpg
└── utilities/
    ├── MetObjectsWithHeightAndWeight.csv   # Source data (127MB), not served
    └── height_from_met_objects.py          # Pre-processing script
```

## Visual Design
Follows `pose_match/` conventions:
- Dark background (`#002235`)
- Cooper Hewitt font
- Accent color `#00f47b`
- Branding via `branding.js` CSS custom properties
- Canvas layout: 800×600 — webcam left panel (400px), matched objects right panel (400px)
- QR code displayed to the right of the canvas in `#qr-sidebar` (flex sibling, not overlaid); bottom-aligned with the canvas bottom edge
- Fixed logo top-left, About link top-right
